# KEFA AI — Revisión de frontend y consistencia del MVP

**Fecha:** 10 de noviembre de 2026.  
**Base:** `Proyecto_IA_KEFA.zip`; rama observada en el ZIP `feature/KEFA-222-fase-dos-frontend` (`fe4be077`); `biblia-de-proyecto.md`, `control-de-estado.md` y `flujo-de-trabajo.md`.

> El Control de Estado y la Biblia reflejan decisiones de octubre. Este reporte describe lo inspeccionado en el ZIP recibido; no implica que Jira, GitHub remoto, Docker o las API externas se hayan verificado en vivo.

## Errores encontrados y correcciones

| Módulo | Hallazgo | Corrección |
|---|---|---|
| Django | `corsheaders` estaba dos veces en `INSTALLED_APPS`; esto puede impedir el arranque | Registro duplicado eliminado y test de configuración añadido |
| Django | `CorsMiddleware` estaba duplicado | Una instancia, después de `SecurityMiddleware` |
| Registro e identidad | El login por correo elegía el primer usuario de una posible lista de emails duplicados | Registro nuevo rechaza correos duplicados (sin distinción de mayúsculas) y el login rechaza coincidencias ambiguas |
| React + API | El formulario de acceso ofrecía solo username pese al soporte de correo en el backend | Login por usuario/correo y pruebas HTTP |
| React + autenticación | Una petición pendiente podía escribir el estado después de cerrar sesión | Versionado de sesión para descartar respuestas obsoletas |
| Layout | Navegación móvil poco cómoda, contenido escaso y diseño visual heterogéneo | Layout reutilizable, responsive, tema claro/oscuro, componentes e iconografía coherentes |
| Páginas | Conversaciones, actividad e integraciones incompletas | UI coherente, preparación local de instrucciones y estados pendientes explícitos; sin simular backend |
| `.env.example` | Incluía `POSTGRES_PASSWORD` aunque Docker usa `POSTGRES_PASSWORD_FILE`, combinación incompatible | Eliminado valor plano de la plantilla; mantener secreto real fuera de Git |
| Docker | Puerto backend `8080` fijo pese a documentarse configurable | `${BACKEND_HOST_PORT:-8080}` |
| README frontend | Indicaba incorrectamente que JWT y varias páginas no existían | Documentación actualizada |
| Seguridad de entrega | El ZIP original incluía `.git`, `.env` y un secreto de PostgreSQL | Distribución saneada sin estos archivos, sin `node_modules` ni `.venv` |

**Nota de revisión para Kevin:** el modelo `users.User` heredado no tiene una restricción `UNIQUE` para `email`. La validación del serializer reduce errores normales, pero **no garantiza unicidad ante registros concurrentes**. El equipo debe evaluar una migración con índice único, saneando antes posibles duplicados existentes, como tarea separada y con respaldo de datos.

## Estado de funcionalidad

**Local únicamente:** redacción, selección de ejemplos y copia de instrucciones. No se envía información a la IA.  
**Interfaz terminada, integración pendiente:** historial, actividad/auditoría, datos de Tasks/Calendar, OAuth, integración n8n y confirmación de acciones sensibles.

## Siguiente fase recomendada: integración funcional del MVP

**Objetivo:** que una instrucción real cruce frontend o Telegram → Django → LLM → validaciones → n8n → Google Calendar/Tasks → registro → usuario, con confirmación cuando proceda.

Definir esquemas de petición/respuesta, idempotencia, seguridad y errores. Registrar nuevas tareas en Jira: no inventar códigos KEFA.
2. **Chat 02 — Backend (Kevin).** Revisar cambios de CORS y emails de esta revisión; añadir modelos de conversaciones y acciones, historial por usuario, endpoints DRF, permisos y tests. Conectar las llamadas al catálogo autorizado.
3. **Chat 03 — IA y Orquestador (Fanny).** Concretar proveedor y el pipeline de extracción/validación de instrucciones a `prepare_tool_call()`, con preguntas de aclaración y confirmación, sin ejecutar código arbitrario.

5. **Chat 05 — Frontend (Alan).** Conectar el editor y las pantallas actuales solo cuando existan endpoints probados; mostrar estados de envío, confirmación, errores, respuestas e historial real. Evitar almacenar instrucciones y credenciales privadas sin necesidad.
